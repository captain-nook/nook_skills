# Nook Skills

这是 Nook 的公开 Codex Skills 发布库。
放已经沉淀成可复用能力的 skill：写作、审校、标题、视觉生成、封面生产、图片 provider，以及少量第三方能力封装。
目标是让以后新增 skill 时，能持续沉淀三件事：

- 这个 skill 当初为了解决什么问题而做；
- 遇到某类工作时应该调用哪个 skill；
- skill 之间如何分工，避免重复造轮子。

## 1. 快速选择

| 你要做的事 | 优先调用 | 说明 |
|---|---|---|
| 从一批采集样本里判断本周该做哪几个选题方向 | `nook-topic` | 选题判断层：受众关、差异化角度、证据先行、关键词设计方法论。不采集、不写稿。 |
| 写微信公众号长文、改稿、从素材成文 | `nook-wechat-writer` | 负责文章角度、结构、正文、摘要、跨平台改写。 |
| 做抖音/小红书/视频号一周内容规划、短视频逐字稿、小红书图文 | `nook-short` | 负责 12 条周内容矩阵、平台采样参考、内容任务书、口播稿和图文页结构。 |
| 给已经定稿的文章取标题 | `nook-title` | 负责标题事实钩子、候选标题、标题评分和事实边界。 |
| 判断一段中文有没有 AI 味、做自然化审校 | `nook-humanizer-zh-review` | 作为写作 skill 的最终审校层，也可单独使用。 |
| 做知识卡片、图文卡片、可视化卡片 | `nook-card` | 负责卡片结构、视觉系统、交付规格。 |
| 做中文演示、slides、可编辑 PPTX | `nook-slides` | 负责内容门、页面形式门、模板驱动 PPTX、duotone-zine 模板包、构建与校验。 |
| 做自驾游路线规划、路书、手机竖屏旅行手册 | `nook-trave` | 负责 8 问收敛、路线方向、地图核算、每日底图、竖屏路书 HTML。 |
| 做小红书/公众号/B站等封面，尤其有标题文字层 | `nook-cover` | 多平台封面生产主 skill，当前重点覆盖小红书封面。 |
| 做视频封面：YouTube/B站/抖音/小红书/视频号 | `nook-tv-cover` | 负责横封面、短封面、竖封面的科技风封面输出。 |
| 用 MiniMax H3 + ComfyUI 生成视频片段、逐条质检并安全重试 | `nook-h3` | 负责 I2VA、FL2VA、L2VA、Ref2VA、T2VA 的官方提示词、物料挂载、UTF-8 提交、顺序轮询、技术/语义质检、失败重跑和断点续跑。 |
| 需要稳定调用 GPT Image 类图片生成能力 | `nook-image-gpt` / `nook-image2-gpt` | 原子图片 provider，供上层视觉 skill 调用。 |
| 需要低成本快速探索图片草稿 | `nook-zimage` | ModelScope Z-Image Turbo，适合草稿、批量探索、低风险素材。 |
| 需要中文海报、封面、高质量文字渲染 | `nook-qwen-image` | ModelScope Qwen-Image，适合中文视觉和更高质量产出。 |
| 需要把一句模糊需求翻译成精准搜索、跨平台/学术/金融/法律等垂类调研并落库 | `nook-search` | AnySearch 之上的搜索中间层，负责意图解释、参数路由、采集编排、结果清洗、存储分发。 |
| 需要第三方中文去 AI 检测/改写参考 | `third_party/Humanizer-zh` | 第三方能力保留，不作为 Nook 主 skill 直接扩写。 |

## 2. 内容生产类

### `nook-topic`

选题判断 skill。管的是"这一堆素材里，哪几个方向真的值得做"，不管采集、不管写稿。

它把选题拆成三段：脚本采（任意实现，不含在本 skill）→ AI 判（语义判断：受众关 → 噪声剔除 → 语义聚类 → 找空隙）→ 人定（AI 只给候选，不拍板）。核心价值在中间那段判断逻辑——尤其是"受众关必须先于热度验证""技术控偏置自检""单条爆款不等于规律"这几条硬规则，都是从真实踩坑里提炼出来的可执行判据。

配套的 `关键词设计推导.md` 单独拿出来也有用：回答"关键词该用受众的症状词、不该用工具名"这件事，给了一个可机械执行的判据和完整的召回体检方法。

适用场景：

- 有一批采集样本（爆款标题、评论区截图、长文收藏），需要判断做哪几个方向；
- 想要一套可审计的选题标准，而不是每次凭感觉；
- 设计/审查采集关键词，判断某个词是不是"技术控视角"而非"受众视角"。

不要用它做：

- 采集本身（本仓库不含采集脚本，见 skill 内 README 说明）；
- 写稿、定标题（选题方向确定之后交给 `nook-wechat-writer` / `nook-short` 这类下游 skill）。

### `nook-wechat-writer`

公众号文章生产主 skill。

它的核心价值是把“想法、素材、转录稿、链接、粗稿”变成一篇可发布的公众号文章。它不是简单写作提示词，而是一套流程：先确认价值点和角度，再组织结构、写正文、做事实检查、做风格审校。

适用场景：

- 从一堆素材里写出公众号文章；
- 修改已有文章，让结构更清楚；
- 把视频脚本、会议记录、读书笔记改成文章；
- 做文章角度确认、摘要、发布字段；
- 文章与短视频脚本之间互相改写。

不要用它做：

- 单独生成标题：用 `nook-title`；
- 单独去 AI 味：用 `nook-humanizer-zh-review`；
- 发布排版、头图尾图装配：应由专门的发布/packager skill 负责。


### `nook-short`

短视频 / 图文内容规划 skill。

它负责把中视频逐字稿、项目复盘、闪念、热点、平台样本，转成抖音、小红书、视频号的一周内容规划。默认结构是抖音 4 条短视频、小红书 2 篇图文 + 2 条视频、视频号 4 条短视频。

适用场景：

- 把一个中视频逐字稿拆成三平台一周内容；
- 根据项目复盘、工具更新、闪念生成内容矩阵；
- 用户问“今天小红书有什么消息”时，用平台样本补充 `live_lane`；
- 写短视频逐字稿、小红书图文页结构和正文；
- 避免一周 12 条都讲同一件事，做审美疲劳检查。

它的核心分工：先规划，再落地。规划层输出内容任务书；落地层再写逐字稿、图文正文和小红书页面结构。

不要用它做：

- 长公众号文章：用 `nook-wechat-writer`；
- 单独标题评分：用 `nook-title`；
- 最终中文去 AI 味审校：用 `nook-humanizer-zh-review`；
- 具体图片生成 provider：用 `nook-image2-gpt` 或对应视觉 skill。
### `nook-title`

标题生成和标题评分 skill。

它解决的是一个很具体的问题：稿件已经写完了，接下来要取几个标题，但标题既要有点击理由，又不能编数字、编榜单、把传言写成事实。

适用场景：

- 在 Obsidian 中 `@` 一篇定稿，然后说“给我取几个标题”；
- 给 AI 资讯、公众号文章、产品更新、工具评测生成候选标题；
- 评估已有标题哪个更适合发布；
- 从一批标题中提炼长度、标点、数字、实体名等规律。

它会先抽事实钩子：实体、数字、动作、冲突、后果、人群、事实边界。再生成高点击版、稳一点的公众号版、搜索友好版，并标注风险。

### `nook-humanizer-zh-review`

中文去 AI 味审校 skill。

它不是“把文字改口语一点”，而是检查文本是不是有典型 AI 痕迹：空泛转折、整齐排比、过度总结、假装有观点、缺少具体细节。

适用场景：

- 文章最终润色前做一遍人味审校；
- 检查视频脚本是否像人在说话；
- 把过于顺滑、过于报告腔的段落改自然；
- 作为 `nook-wechat-writer` 的强制子审校层。

## 3. 视觉与封面类

### `nook-card`

卡片设计 skill。

它用于把信息做成有结构、有视觉语言的卡片，而不是简单把文字贴到图上。适合知识卡片、方法卡片、信息图、社媒传播图。

沉淀原因：

- 卡片类输出容易变成模板堆叠；
- 需要把内容结构、视觉层级、交互动效和交付规格稳定下来；
- 后续可以继续接入 OpenDesign、Remotion、HTML 模板等工作流。

### `nook-cover`

多平台封面生产主 skill。

它面向更完整的封面工作流：理解平台、确定主视觉、生成背景或使用素材、稳定中文标题层、导出对应尺寸。

适用场景：

- 小红书封面；
- 公众号封面；
- B站/YouTube/抖音/视频号等平台封面规划；
- 需要标题文字层稳定落版的封面。

### `nook-slides`

中文演示文稿和可编辑 PPTX 生产 skill。

它的目标不是让模型临场自由设计 PPT，而是把内容确认、页面形式确认、模板包填槽、PPTX 构建和校验固定成一条可复用流程。当前重点支持 `duotone-zine` 双色独立刊物风模板包。

适用场景：

- 从主题、笔记、文章、培训大纲生成中文演示；
- 需要先确认内容结构和每页呈现形式，再生成 PPT；
- 需要可编辑 PPTX，而不是纯图片或一次性截图；
- 需要模板驱动的组件生成器、构建日志、component map 和校验；
- 需要沉淀新的视觉系统模板包。

当前包含：

- `scripts/build_deck.py`：读取 `deck_plan.json`，生成可编辑 PPTX；
- `scripts/validate_deck.py`：检查 PPTX 包结构、页数、施工污染词；
- `scripts/diagnose_deck.py`：检查文本框数量、字符量、shape 数、黑块数量等粗指标；
- `assets/templates/duotone-zine/`：双色独立刊物风组件库 PPTX 和源脚本；
- `references/duotone-zine-template-package.md`：模板包执行契约。

重要边界：

- 不能把项目成品 PPT、用户素材、Obsidian 笔记过程文件提交进本仓库；
- 不能把模板当作灵感图后自由重画，生成阶段应按模板包填槽；
- 结构校验不能替代 PowerPoint 实际渲染复核，特别是中文自动换行和标点孤行。
### `nook-tv-cover`

视频封面专项 skill。

它聚焦横封面、短封面、竖封面三类视频平台封面，默认偏科技风、内容感、信息密度较高的视觉方向。

适用场景：

- YouTube 长封面；
- B站短封面；
- 抖音/小红书/视频号竖封面；
- 视频内容主视觉与标题组合。

## 4. 图片 Provider 类

这些 skill 更像底层能力，不一定直接面向最终内容。上层视觉 skill 可以根据质量、成本、速度来调用它们。

### `nook-image-gpt`

早期 GPT Image 相关图片生成 provider。保留用于兼容已有流程。

### `nook-image2-gpt`

更偏原子能力的 GPT Image provider，适合稳定的文生图和图生图任务，也适合被更大的视觉 skill 调用。

### `nook-zimage`

低成本快速文生图 provider。

适合：

- 草稿探索；
- 批量试方向；
- 背景图、低风险素材；
- 不需要最高质量但需要速度和成本控制的任务。

### `nook-qwen-image`

中文视觉质量更高的图片 provider。

适合：

- 中文海报；
- 中文封面；
- 标题型视觉；
- 对中文文字渲染要求更高的图像任务。

## 5. 旅行与路书类

### `nook-trave`

自驾旅行路书规划 skill。它把一句旅行意图收敛成可执行的随车路书，当前首个完整样例是“成都出发，新疆全程自驾，不超过 26 天”。

它的核心流程是：开场仪式、单问单答 8 个问题、路线方向确认、地图过程可见、里程和时长核算、每日底图生成、手机竖屏 HTML 路书交付。

适用场景：

- 用户只有出发地、目的地和天数，需要先被温和地问清偏好；
- 需要把长线自驾拆成每日节奏、住宿点、驾驶强度和景区安排；
- 需要在生成路书前后用高德数据做里程和时长校验；
- 需要把总览地图和每日静态底图整合进最终稿件。

重要边界：

- 它不是实时导航工具；
- 酒店、天气、道路管制、景区政策和边防证要求需要出发前复核；
- 高德 key 只能通过 `AMAP_WEB_SERVICE_KEY` 或临时命令参数传入，不进入仓库。

## 6. 检索与调研类

### `nook-search`

AnySearch 之上的搜索中间层 skill。

AnySearch 是一个覆盖 17 个垂直领域（社交平台、学术论文、金融数据、法律文书、代码库等）的 Agent 搜索 CLI，但它本身只负责"按参数取数"，不懂人话、不做清洗、不管落盘。`nook-search` 补上了意图解释、参数路由、采集编排、结果清洗、存储分发这五环，把它变成可被其他 skill 直接嵌入调用的搜索基础设施。

适用场景：

- 把一句模糊需求（"帮我查一下 XX 最近的动态"）翻译成精准的 AnySearch 查询；
- 需要跨平台（X / Reddit / 知乎 / 微博 / 微信公众号）调性对比或选题调研；
- 需要学术、金融、法律等垂类数据支撑写作或调研；
- 需要合规可商用的配图素材采购（License 三色标注）；
- 上层写作/调研类 skill 需要"先搜再写"，作为原子搜索能力被嵌入。

重要说明：本 skill **不包含** AnySearch 的代码，属于独立第三方开源项目，需要单独部署，使用前请先看 `nook-search/README.md` 里的部署方式和 API Key 获取方式。

不要用它做：

- 国内需登录平台（小红书/抖音/B站等）的采集：AnySearch 不支持，需另配专门工具；
- 写稿、选题、出图：搜完只交数据，不做下游生产。

## 7. 第三方能力

### `third_party/Humanizer-zh`

第三方中文去 AI 检测/改写能力保留区。

它不是 Nook 原生写作方法本身，而是作为参考和对照，帮助 `nook-humanizer-zh-review` 沉淀更具体的审校规则。

## 8. 维护原则

### 8.1 什么应该进入这个仓库

- 已经可以被 Codex 调用的发布态 skill；
- 对应的 `SKILL.md`、`agents/openai.yaml`、`references/`、`scripts/`、必要资产；
- 能解释 skill 使用边界的 README 或参考文件；
- 可复用、可迁移、可公开的工作流。

### 8.2 什么不应该进入这个仓库

- Obsidian 笔记库内容；
- 个人素材、临时讨论、未清洗截图；
- 私密路径、token、账号信息；
- 只服务某一次任务的过程文件；
- 还在建设中的半成品 skill。

建设态内容应该先放在私有工作区，确认可复用后再发布到这里。

### 8.3 新增 skill 时要补什么

新增一个 skill 时，至少补齐：

- `SKILL.md`：触发描述要清楚，说明什么时候用；
- `README.md`：给人看的用途说明；
- `agents/openai.yaml`：给 Codex UI 识别；
- `references/`：只放真正需要复用的规则和样例；
- `scripts/`：只放确定性高、反复会用的脚本；
- 根 README：把这个 skill 加入“快速选择”和对应分类。

## 10. 视频生成与 ComfyUI

### `nook-h3`

`nook-h3` 是 MiniMax H3 + ComfyUI 的本地视频生成编排 Skill。它不绑定某个项目、某个故事或固定镜头数量，而是把项目差异放进外部任务清单，把容易出错的提交和监听流程固定下来。

它适合以下工作：

- 根据分镜选择 I2VA、FL2VA、L2VA、Ref2VA 或 T2VA；
- 按官方 H3 规范整理提示词和对白；
- 提交前自动校验官方字段顺序、对白标签、无 BGM 设置，并可按镜头拦截灾难式云海词汇与画外迟入场；
- 挂载首帧、尾帧、人物设定图、场景图和道具参考图；
- 通过 UTF-8 API 提交中文提示词；
- 每条推理完成后强制暂停在 `awaiting_qc`，未质检不提交下一条；
- 自动输出接触表、技术报告和标准 WAV；台词镜头可做离线中文识别证据；
- 检查主体构图、肢体、跟随运镜、手持呼吸感、云层运动、台词和现场声音；
- 对失败任务更换种子、修订官方提示词并使用新输出前缀重跑；
- 保存状态支持断点续跑；
- 批量处理任意数量的片段，不需要为 3 条、7 条或 100 条任务重新写脚本。

#### 最小使用方式

准备自己的 ComfyUI 工作流、输入图片和 `h3_tasks.json` 后：

```powershell
powershell -ExecutionPolicy Bypass -File .\nook-h3\scripts\run_h3_batch.ps1 `
  -ManifestPath .\h3_tasks.json
```

任务数量由 JSON 中的 `tasks` 数组决定。每个 task 代表一段待生成的视频素材；一条最终成片可以由多个 task 组成。多个最终视频可以分别维护 manifest，也可以在一个总 manifest 中通过 `video_id` 区分。

详细说明见 [`nook-h3/README.md`](nook-h3/README.md)，官方 H3 提示词规范需要单独安装 `h3-prompt-writing` Skill。
