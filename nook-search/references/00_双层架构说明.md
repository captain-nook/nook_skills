# 00 双层架构说明

## 0.1 为什么必须分两层

把搜索能力拆成"前端工具" + "Skill 中间层"，不是为了概念清晰，是为了**解决三个真实痛点**：

1. **可复用性差**：AnySearch 本身是一个 CLI，每次用都要重新拼命令、重新调参数、重新设计清洗逻辑——其他 skill 想用，复制粘贴一遍。
2. **不懂人话**：AnySearch 是"参数化的 API"，看不懂"今晚的电影票"。需要一个"翻译官"。
3. **结果不干净**：AnySearch 返回结构化 JSON + Markdown，但字段命名是英文、时间戳是 ISO、License 是 license 字段——直接给用户看要再做一遍翻译。

Skill 中间层 = 把"翻译 + 编排 + 清洗 + 存储"四件事固化下来，让 AnySearch 变成可复用的"AI Agent 搜索基础设施"。

## 0.2 两层的职责边界

| 维度 | AnySearch（前端） | nook-search（Skill） |
|---|---|---|
| 角色 | 原子工具 | 中间层 / 编排层 |
| 输入 | CLI 命令 + 参数 | 一句人话需求 + 上层 skill 的 schema 调用 |
| 输出 | 原始 JSON / 原始 Markdown | 清洗后的 Markdown + 元信息 + 落库 |
| 状态 | 无状态 | 维护路由规则表 + 模板 + 路径契约 |
| 复用方式 | 每次重新调 | 被其他 skill 嵌入（暴露 5 环 schema） |
| 失败处理 | 抛错 / 返回空 | 标 `partial: true` + 降级 + 写入失败原因 |
| 升级影响 | 命令参数 / 域列表 | Skill 内部维护映射，**上层零感知** |

**判断红线**：任何"用 AnySearch"的请求**先过 Skill**。直接调 CLI 的场景只允许一种：调试 / 验证 AnySearch 本身。

## 0.3 Skill 的封装价值（为什么是"原子 skill"）

nook-search 自己就是一个**可被嵌入**的原子 skill。当其他上层 skill（选题、写稿、调研类）需要"先搜再写"时，它们调用 nook-search 的 5 环 schema，**不直接调 AnySearch**。

封装带来的好处：
- **AnySearch 升级不波上层**：如果 AnySearch v3 把 `social_media.social_media` 改名为 `social_media.platform`，改 `domain_map.yaml` 就行，上层 skill 不动。
- **跨 skill 复用一致**：选题的"跨平台热点"和公众号的"跨平台背景资料"走的是同一套 5 环，命令组合和清洗模板是同一份。
- **失败处理统一**：上层 skill 不用关心"AnySearch 报 Connection Error 怎么办"——Skill 已经标 `partial: true` + 写了降级策略。

## 0.4 与其他 skill 的关系

nook-search 定位是**中间层**：往下调用 AnySearch CLI 这个原子工具，往上被其他业务 skill（选题、写稿、调研类）嵌入调用。

| 层级 | 角色 | 职责 |
|---|---|---|
| 工具层 | AnySearch CLI | 原子搜索，只按 query 取数 |
| **搜索 Skill 层** | **nook-search（本 skill）** | **AnySearch 之上，管理意图-路由-编排-清洗-存储五环** |
| 业务层 | 上层 skill（选题 / 调研 / 写稿等） | 只调用 nook-search 的五环 schema，不直接接触 AnySearch CLI |

覆盖范围：X / Reddit / LinkedIn / 微信公众号（搜狗通道）/ 微博 / 知乎 / 学术 / 金融 / 法律 / 通用网页 / 资源图等 AnySearch 支持的域。需登录的国内平台（小红书/抖音/B站/视频号）不在覆盖范围内，需要另配专门的采集工具。
