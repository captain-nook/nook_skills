# 03 采集编排（环 3）

## 3.1 这一环解决什么问题

路由表定下来后，Skill 要决定：**怎么把这些 query 跑起来**——并行还是串行？哪些先跑？失败怎么办？日志怎么落？

AnySearch 本身是命令行的子命令，没有"任务编排"能力。Skill 的环 3 = 补上这一层。

## 3.2 核心 Schema

```yaml
orchestration:
  strategy: parallel | serial | mixed
  batches:
    - batch_id: 1
      steps:
        - id: 1
          type: search
          cmd: "anysearch_cli.py search 'AI Agent 教程' --domain social_media --sub_domain social_media.social_media --sdp 'type=zhihu,keyword=AI Agent 教程' --max_results 5"
          timeout_s: 10
          retry: 2
          on_fail: skip   # skip / abort / fallback
        - id: 2
          type: batch_search
          cmd: "anysearch_cli.py batch_search --queries '[{\"query\":\"...\",\"domain\":\"...\"},...]'"
          timeout_s: 15
          retry: 1
          on_fail: partial   # batch_search 失败 → 部分成功也要保留
      interval_s: 0
  total_budget_s: 60
  # 运行日志不单独存文件，作为「采集过程」小节写入同一个 YYMMDD_主题.md（扁平单文件，见 05_存储分发）
  log_level: info
  capture:
    - stdout
    - stderr
    - duration_ms
    - exit_code
```

## 3.3 编排规则

### 3.3.1 优先 batch_search（≤5 路并发）

实测：3 路 batch_search ≈ 3 秒，比单条串行（3×3=9 秒）快 3 倍。

```bash
# 推荐：batch_search
anysearch_cli.py batch_search --queries '[
  {"query":"AI 工具","domain":"social_media","sub_domain":"social_media.social_media","sub_domain_params":"type=zhihu_hot"},
  {"query":"AI 工具","domain":"social_media","sub_domain":"social_media.social_media","sub_domain_params":"type=x_top"},
  {"query":"AI 工具","domain":"social_media","sub_domain":"social_media.social_media","sub_domain_params":"type=reddit_post"}
]'
```

### 3.3.2 独立步骤并行，依赖步骤串行

```yaml
# 例：先拿到 Reddit 帖子 URL，再 extract 详情页
steps:
  - id: 1
    type: search
    cmd: "...type=reddit_post,keyword=AI Agent..."
  - id: 2
    type: extract
    cmd: "anysearch_cli.py extract '<url_from_step_1>'"
    depends_on: [1]
```

### 3.3.3 失败可降级，不静默

三种降级策略：

| 策略 | 适用 | 行为 |
|---|---|---|
| `skip` | 单条 query 不影响大局 | 跳过此条，继续跑其他 |
| `partial` | batch_search 部分失败 | 保留成功的，标失败的为 `null` |
| `abort` | 关键步骤失败 | 整批中止，标 `failed: true` |
| `fallback` | 主域不可用 | 切到备选 query 重试 |

**禁止**：返回空结果冒充成功。任何 `failed` 必须标在 `partial_results` 字段。

### 3.3.4 总额度按 1,000 次/天控

```yaml
quota:
  used_today: 47       # Skill 内部计数
  limit_per_day: 1000
  warn_threshold: 800  # 超过 80% 触发用户告警
```

超额触发前向用户告警：
> "今日 AnySearch 调用已达 820/1000，建议升级 Pro 或分批。"

### 3.3.5 日志落盘

每步的 stdout / stderr / duration_ms / exit_code 必须落盘到 `log_dir`。日志格式：

```log
[2026-07-20 17:43:12] step_id=1 type=search status=ok duration_ms=1245
[2026-07-20 17:43:12] step_id=2 type=batch_search status=partial duration_ms=3210
  - query_1: ok (5 results)
  - query_2: ok (5 results)
  - query_3: failed (ConnectionError)
```

## 3.4 示例：跨平台调性对比

```yaml
orchestration:
  strategy: parallel
  batches:
    - batch_id: 1
      steps:
        - id: 1
          type: batch_search
          cmd: |
            anysearch_cli.py batch_search --queries '[
              {"query":"AI 工具","domain":"social_media","sub_domain":"social_media.social_media","sub_domain_params":"type=zhihu_hot"},
              {"query":"AI 工具","domain":"social_media","sub_domain":"social_media.social_media","sub_domain_params":"type=x_top"},
              {"query":"AI 工具","domain":"social_media","sub_domain":"social_media.social_media","sub_domain_params":"type=reddit_post"},
              {"query":"AI 工具","domain":"social_media","sub_domain":"social_media.social_media","sub_domain_params":"type=wechatmp"},
              {"query":"AI 工具","domain":"social_media","sub_domain":"social_media.social_media","sub_domain_params":"type=weibo_hot"}

          retry: 1
          on_fail: partial

```

实测：5 路 batch_search ≈ 3-5 秒拿到 5 平台对比表。

## 3.5 失败恢复模式

| 失败模式 | 表现 | 处理 |
|---|---|---|
| Connection Error | 单次偶发 | retry 2 次，仍失败 → `skip` |
| QPS 超限 | batch_search 部分 query 失败 | 标 `partial` + 记录 + 不重试（避免连锁） |
| Domain 不可用 | 整个域返回 0 结果 | `fallback` 切到 `general` |
| 401 / API key 失效 | 鉴权失败 | 立即 `abort` + 提示用户检查 key |
| 超时 | 单步 > timeout_s | `abort` 当前 step + `partial` 保留已完成 |
| GBK / mojibake（编码乱码） | Windows 默认 GBK，CLI 中文返回成乱码（如 "鏌ユ煡"）；或脚本写文件抛 `UnicodeEncodeError`；日志里出现替换字符 `\ufffd` | 启动前 `chcp 65001` + `PYTHONIOENCODING=utf-8` + `PYTHONUTF8=1`；落盘显式 `encoding="utf-8"`；清洗层检测到 mojibake（高频非可读字符 / `\ufffd` 占比 > 1%）→ 标 `partial: true` + 修复编码后重跑该步；连续 2 次仍乱码 → `fallback` 切 `general` 域并降级到英文关键词 |
| 时间窗口不支持（social_media 域） | 用户要"72h/24h/本周"但 social_media sdp 无 time/period 参数；返回结果无 `published_at` 字段；硬过滤无法执行 | 翻译层降级：① 把时间词写进 query 自然语言（"AI news in the last 72 hours"）；② 若话题相关切到 finance（period）/ academic（year_from）；③ 呈现层标 `time_window_check: FAILED` + 保留全部结果 + 按 Score 降序作为热度代理；④ 需严格过滤提示用户走 extract 二次抓取详情页拿时间戳。**禁止静默忽略**（违反硬规则 8 + 15） |
| PowerShell 重定向破坏 UTF-8 | `Tee-Object -Append` 导致 raw 文件出现 2 份输出；`>` 默认 UTF-16；`Out-File -Encoding utf8` 带 BOM | Windows 环境捕获 stdout 必须用 `Start-Process -RedirectStandardOutput`（底层句柄）或 `[System.IO.File]::WriteAllText` + `UTF8Encoding(false)`；**禁止**用 PowerShell 原生 `>` 或 `Tee-Object` |
| batch_search 内部缓存/重试 | 相同 query 短时间内重跑返回 cost_ms=1ms（缓存命中）；raw 文件偶现 2 份完整输出（疑似内部重试） | 这是 AnySearch 后端正常行为，不是错误。同 query 重跑拿到 1ms 是缓存命中；重复输出取最新一份即可，不需 retry |
| 查询路径与文件扩展名不一致 | AnySearch 默认返回 markdown 字符串，但曾被错误命名为 `.json` | raw 文件扩展名必须与实际内容一致：AnySearch 默认输出 markdown → 文件名用 `.md`；仅当 live API 显式返回 JSON 结构时才用 `.json` |

## 3.6 与其他环的契约

- **环 2 输出 = 环 3 输入**（路由表直接驱动编排）
- **环 3 输出 = 环 4 输入**（编排结果 JSON / 原始 Markdown 交给清洗层）
