## 0.1 Skill 架构与环境解耦

本 Skill 将外部知识输入、原子卡片沉淀、创作选题推导与双链质检整合成一套流水线。工作时根据用户意图自动进入对应的子流程：
- **Ingest 模式（提炼入库）**：触发词如「整理一下」「入库」「清库」「处理这几篇文章」。
- **Query 模式（选题推导）**：触发词如「找选题」「看看能写什么」「这期写什么」「我想做个关于某某的内容」。
- **Lint 模式（质量体检）**：触发词如「检查Wiki」「体检」「查查知识库」「检查链接质量」。

### 目录与配置文件自适应
启动任何模式前，Agent 自动检测当前工作区目录并映射，无需用户强制按照特定前缀组织：
1. **输入目录（Clipper / Inbox）**：优先查找 `01_Clipper/` 或 `Clipper/`（剪藏原文，只读）；`00_Inbox/` 或 `Inbox/`（临时速记）。
2. **知识库目录（Wiki）**：优先查找 `02_Wiki/` 或 `Wiki/` 或 `Notes/`（卡片与话题页平铺存放处）。
3. **输出目录（Topics）**：优先查找 `03_选题/` 或 `Topics/` 或 `03_Topics/`。
4. **创作者档案（Profile）**：优先读取根目录下的 `profile.md` 或 `关于我.md`；若两者皆不存在，使用通用的客观创作者准则（见 `profile.example.md`），并在合适时机建议用户建立。
5. **底层规则与模板（Schema）**：优先读取本地 `80_Schema/nook wiki Schema.md` 与 `80_Schema/模板 选题卡.md`；若本地不存在，直接以本 Skill 内置的 `references/schema.md` 与 `references/topic_card_template.md` 作为基准规则。

## 0.2 Ingest 模式：提炼入库

把新剪藏的原文和 Inbox 里的速记，提炼成原子卡片与话题页。

### 0.2.1 写入范围
只在 Wiki 目录新建或修改文件。原文目录只读，一个字不动。Inbox 目录只读，每条去向列清单交给用户拍板。

### 0.2.2 开始前准备
1. 读完 Schema 规范与创作者 Profile。
2. 列出 Clipper、Inbox、Wiki 目录的当前实际文件，以实际存在的文件为准。
3. 读 Wiki 目录下的 `_log.md` 与 `_index.md`（不存在则新建空文件）：
   - 比对 Clipper 文件名与原文属性里的 `source` / `source_url`，未在 `_log.md` 出现的为待处理原文。
   - 日志结果为 `暂缓` 或 `部分完成` 的，列为可重新处理。
   - 搜寻半成品：在 Wiki 目录中搜索卡片来源，若指向某篇原文但在 `_log.md` 中无记录，先读取已有卡片，对着原文补齐剩余部分后记日志，不从头重复做。
4. 向用户报一句计划：待处理几篇原文、几条 Inbox，按 `created` 顺序排列，超过 10 篇建议分批。**停下等待用户确认后，再开始第一篇。**

### 0.2.3 逐篇处理（严禁批量脚本）
单篇从通读到播报全部完成，再打开下一篇。播报完一篇紧接着打开下一篇，中途不等回复；整批做完并复查后汇报。
1. **通读**：从头到尾完整阅读文字，长文分段读，图片跳过。
2. **判断能否加工**：内容过短或无实质论述的，能提炼则提炼，否则记为暂缓；与已有内容为同一篇转载的，补充已有卡片来源并记为无新增。
3. **找候选内容**：
   - 判据：离开原文后能否被拿来支持、反驳或讲清某个具体判断（依据、案例、反例、实操方法）。跳过自我介绍、广告引流、普遍常识与纯导读。
   - 以回答的问题为聚合单元，能回答同一问题的候选合并为一张卡片。避免按原文小标题机械切分。
4. **与已有积累比较**：在 Wiki 目录检索关键词，命中卡片后选择：
   - `新建`：库内尚无此说法。
   - `补充`：已有卡片讲同一件事，本文带来新论据/条件/案例，补充正文并增加来源。
   - `保留差异`：说法相近但对象、条件或结论不同，新建卡片并在两卡正文中互相双向链接并附带理由。
   - `无新增`：已有卡片已完整覆盖。
5. **写卡**：
   - 文件名写核心说法，使用原文词汇，保留归属（非第一手不写成定论）。
   - 正文严格分离四种声音：原话（`> ` 加说话人）、转述、推断（标 `【推断】`）、用户的话（标 `【创作者】`）。
6. **写完立即自检**：
   - 每一句原话回原文检索，必须是同段连续文本，一字不差。搜不到改转述或删除。
   - 每个数字核对口径、单位、时间与统计对象。
   - 说话人归属与转引链核对无误。
7. **更新话题页**：
   - 检查卡片话题标签：当至少两位不同作者的卡片讨论同一问题且尚未建页时，当场新建话题页；已有话题页则重读相关卡片，更新综合认识，并确保每一句都有卡片支撑，防止指标对象说反。
8. **记日志与导航**：
   - `_log.md` 追加单行记录：`日期｜原文文件名｜原文链接｜结果｜产出卡片或原因`。
   - `_index.md` 增补卡片与话题页。
9. **逐篇播报**：汇报候选问题、处理方式、新建链接、未收录小节及话题页变动。

### 0.2.4 处理 Inbox
逐条读取 Inbox，区分为原文收藏理由（记入对应卡片）、用户个人观点/亲历（按标准成卡，标【创作者】）、杂记代办（保留）。处理前列清单给用户确认。

### 0.2.5 本批结束与做完标准
- 抽查三分之一新建/补充卡片（至少 3 张）回原文核对原话和数据，新建/更新的话题页全量复查。
- 向用户总结汇报实际完成数量（处理篇数、新建/补充/差异/无新增卡片数、话题页变化、待核验项）。

## 0.3 Query 模式：选题推导

从库内材料与创作者经历中推导高质量选题，由用户拍板并生成选题卡。

### 0.3.1 写入范围
只在 Topics（选题）目录新建或修改选题卡。原文与 Wiki 目录只读。

### 0.3.2 开始前准备
1. 读创作者 Profile（定位、受众、文字硬规矩）。
2. 读选题卡模板。
3. 读 `_index.md` 与已有选题卡，避免重复推导已在推进的选题。

### 0.3.3 先问用户（单次单问）
根据用户开场逐步收敛，**一次只问一个问题**，原样捕捉创作者的一手经历与核心原话：
- 模糊开场（如“看看能写什么”）：询问最近经历的典型事件或思考。
- 给出方向（如“想做对标账号”）：询问其在该方向上的真实踩坑或最想表达的一句话。
- 已有观点：直接进入材料匹配，同步检索支持与反对论据。

### 0.3.4 拿库内材料回应
1. 检索话题页与卡片，找到与讨论议题强相关的支撑证据。
2. 核对关键原话与数据，组织成 2~3 个有真实差异的方向：
   - 一句话观点（这期要让受众接受的核心判断）。
   - 受众与痛点（解决 Profile 中读者的什么问题）。
   - 创作者原话（用户在沟通中给出的真实经历）。
   - 依据（库内哪几张卡片支撑）。
   - 反例与限制（库内冲突或限定范围的卡片）。
   - 还缺什么（缺少哪类外部材料，或需创作者补充什么细节）。
3. 若材料不足以支撑多个方向，如实告知缺口，建议补充采集。

### 0.3.5 生成选题卡
经用户选定并确认后，在 Topics 目录新建 `YYMMDD 一句话观点.md`：
- 状态如实标为 `可写`、`待补料` 或 `种子`。
- 填入观点、创作者原话、依据卡片双链；无内容的空章节整节删掉。
- 生成后向用户呈现，经确认即为定稿。

## 0.4 Lint 模式：知识库体检

检查 Wiki 目录的结构完整性、内容保真度与引用网络。

### 0.4.1 写入范围与权限
只修改 Wiki 目录文件。原文只读。机械性问题直接修复并记入日志；涉及观点理解、卡片合并/拆分/删除等决策，列清单由用户确认。

### 0.4.2 结构检查（可机械化定位与修复）
1. **来源链接有效性**：卡片 Frontmatter 里的原文引用是否为规范双链，对应原文文件是否存在。
2. **断链检查**：正文中的双链指向的页面是否存在（卡片属性中的候选话题暂无页面属正常状态，不算断链）。
3. **单向链接补全**：A 卡正文链接 B 卡，B 卡正文末尾需对称补上回链与关联理由。
4. **候选话题建页提醒**：同一话题已被两位以上独立作者使用却未建页的，提示用户。
5. **控制文件完整性**：检查 `_index.md` 是否漏收卡片，`_log.md` 是否完整记录。

### 0.4.3 内容检查（抽查核对）
1. **原话核对**：抽查卡片引用，确认是否同段连续、一字不改。
2. **数字核验**：确认卡片数据与原文口径完全一致。
3. **话题页防翻转**：
   - 核对“都”、“几位”等综合句是否强行归属。
   - 核对数字指标在综合为话题页时，限定对象或方向（如不低于/不高于、占比分母）是否反转。
4. **用法检查**：筛查未被任何页面链接的孤立卡、按章节过细切分的卡片、以及过于宽泛的话题页。

### 0.4.4 汇报与修复日志
直接修复的问题在 `_log.md` 追加单行记录：`日期｜检查｜—｜—｜修复了什么`。需用户判断的事项，明确呈现问题所在文件、涉及原话、潜在影响与建议方案。
